This is what your documentation looks like on disk.

Your docs root is the folder the project is configured to read — `docs/` in this example.

```text
docs/
├── d360.json                    the navigation manifest
├── .document360/                reuse objects, committed with the content
│   ├── tags.json
│   ├── labels.json
│   ├── variables.json
│   └── snippets/
│       └── global/
│           └── <name>.md
└── en/                          one folder per language
    ├── <category>/
    │   ├── README.md            the category's own page
    │   └── <article>.md
    └── api-reference/           API reference storage, where a project has one
        └── <slug>/
            ├── README.md
            └── openapi.yaml
```

## `d360.json`

The manifest that places every page in the tree. **Order in the file is order in the navigation.**

```json
{
  "serializerVersion": 1,
  "languages": [{ "code": "en", "default": true }],
  "nodes": [
    {
      "paths": [{ "langs": ["en"], "path": "start-here/README.md" }],
      "children": [
        { "paths": [{ "langs": ["en"], "path": "start-here/your-first-change.md" }] }
      ]
    }
  ]
}
```

Each node carries `paths`, which maps languages to a language-relative file path, and an optional
`children`. A node with children is a category; a node without is an article.

> [!IMPORTANT]
> **Moving a page in the navigation is an edit to this file, not a move on disk**
>
> The file's location and its position in the tree are separate facts. You can reorder the whole
> knowledge base without renaming a single file — and that also means a file renamed on disk must be
> renamed here, or it leaves the tree.

## `.document360/`

Your reuse objects, stored as files so they are versioned and reviewed like everything else.

[d360]: # 'table border="all" striped="true"'

| File | Holds |
| :--- | :--- |
| `tags.json` | Tag groups and tags |
| `labels.json` | Label groups and labels |
| `variables.json` | Variables and their values |
| `snippets/global/<name>.md` | A snippet, one file each |

[d360]: # "/table"

Catalogue entries carry no `guid`. The import merge matches a tag or a label by its `uniqueId`, a
tag group or label group by its name, and a variable by its name.

> [!NOTE]
> **The glossary is here too, shaped differently**
>
> Tags, labels and variables are catalogue files; a glossary term is one Markdown file per term, in
> the workspace's glossary folder, with the term and its aliases in front matter and the definition
> in the body. Like the catalogues, it syncs both ways.

## `en/`, and the language folders

Every piece of content sits under a language folder. `en/` here, and a sibling folder per additional
language, each holding the same paths.

## Categories and `README.md`

A folder is a category, and its `README.md` is the category's own page. The `type` in that file's
front matter says what kind of category it is:

| `type` | The category page is |
| :--- | :--- |
| `page` | A page with its own content |
| `index` | A page that links straight to its first article |
| *absent* | A plain folder with no page of its own |

## `api-reference/`

Where a project has an API reference, it lives in `api-reference/<slug>/` as a `README.md` plus
exactly one spec file.

> [!TIP]
> **`api-reference/` is storage, not a position**
>
> Where the reference *appears* is decided by `d360.json`, like everything else. The folder's name
> says what the content is, not where readers find it — so an API reference can sit anywhere in your
> navigation, including in the middle of your guides.

## What you will not find

- No build output. The knowledge base site is generated by Document360, not committed.
- No database export. The files are the content.
- No lock file or index that you have to keep in step by hand.
